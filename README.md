# Errand Agent

A chat agent that arranges home-service errands (plumber, electrician, AC servicing, cleaning ...) against a local
mock marketplace. It clarifies missing details, compares providers, asks for approval before anything consequential,
and recovers safely from tool failures. Everything runs locally: no real providers, payments or integrations.

Safety is structural, not prompt-based: the model can only read and *propose*. Deterministic code decides approval and
is the only thing that can book, cancel or reschedule. [`DESIGN.md`](DESIGN.md) explains how.

## Quick start

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
pytest                      # the whole suite, offline: no API key is needed and network access is blocked
python -m demo              # chat with the agent in the terminal (needs ANTHROPIC_API_KEY, see Configuration)
python -m demo.web          # or in the browser: http://127.0.0.1:8000
python -m errand.trace.cli follow   # in a second terminal pane: the live trace
```

## Running the tests

`pytest` runs everything, including the end-to-end scenarios in `tests/evals/` (each runs the real graph,
guard, executor and mock world with a `ScriptedModel`; assertions are on DB state and trace events, never reply
wording). Every test runs with no API key and with socket connections blocked, so nothing can reach a real model. The
safety invariants (no booking without a valid approval, at most one booking per idempotency key, no success claim
without a verified attempt) are checked on every agent and eval scenario.

## The demo

```bash
python -m demo                 # data lives in ./.errand (git-ignored)
python -m demo --fresh         # wipe it and reseed
python -m demo --random        # contract failure rates for book (see below)
python -m demo --fake-clock    # fake time you can move with /advance 11m
```

| Flag | Effect |
|---|---|
| `--random` | **Turns on the 70/15/15 contract rates for `book`: 70% success, 15% `slot_taken`, 15% timeout (half of the timeouts actually booked).** Applies when the world is created; without it the world has no random failures and you trigger failures with the commands below. |
| `--fresh` | wipe the demo data and reseed (only a folder this tool created) |
| `--fake-clock` | fake time, moved with `/advance 11m` (for example to let a hold expire) |
| `--session NAME` | the conversation to continue (default `demo`) |

The demo user is seeded with 56 saved memories (some are traps: forgotten, unconfirmed or replaced), an 84-turn earlier
conversation and a booking history (past electricians, an upcoming AC servicing and an upcoming cleaning). The three
example requests work end to end:

- "Find a plumber for my kitchen tap this week, mornings only, under ₹1,500."
- "Move my AC servicing to Saturday."
- "Book the same electrician as last time, but not before 10 a.m."

### Triggering failures on cue

These commands drive the mock world's simulator hooks; they are not agent tools. `/help` lists them all.

| Command | Effect |
|---|---|
| `/demo timeout` | the next booking commits and then times out; the trace shows `tool_error timeout` -> `get_booking_status` -> confirmed |
| `/demo injection` | ask about `pl_01`'s reviews, which contain a planted instruction; the trace shows `untrusted_scan`, and nothing is booked without your "yes" |
| `/demo cancel`, `/provider-cancel [cleaning\|ac\|<booking_id>]` | the provider cancels; the agent finds out by polling, tells you once and proposes a replacement for your approval |
| `/timeout [after\|before]`, `/price +200`, `/slot-taken`, `/force <tool> <kind> [n]` | a timeout, a price change, a taken slot, any forced outcome (`/force list`, `/force clear`) |

Kill the CLI at any point and start it again: startup recovery settles any half-finished booking against the
marketplace's own status and never books twice.

### Suggested 3-5 minute recording

1. `python -m demo --fresh`, trace pane beside it. Ask for the first example request; approve; show the trace.
2. `/demo timeout`, repeat a booking: the timeout is resolved through `get_booking_status`, one `book` call.
3. `/demo injection`: the planted instruction is wrapped and flagged, and nothing happens without approval.
4. `/demo cancel`: the notice and the replacement proposal, then "yes".

## The web UI

```bash
python -m demo.web                      # http://127.0.0.1:8000 (localhost only)
python -m demo.web --port 8080 --poll-seconds 2
```

The same agent in the browser: the chat on the left, my bookings and the live trace on the right, the demo failure
buttons and a light/dark toggle along the bottom. It is one static page styled by `demo/web/theme.css` (a warm cream,
crimson and amber theme: subtle borders, soft shadows), with no build step; the server is a small FastAPI app in
`demo/web/server.py`. Text is Poppins and trace rows, pills and timestamps are IBM Plex Mono, both loaded from Google
Fonts; the server's Content-Security-Policy allows only `fonts.googleapis.com` and `fonts.gstatic.com`, and offline the
page falls back to system fonts.

- **The page can never book.** Its Confirm and Decline buttons only send the displayed text (`CONFIRM <code>` / `no`)
  through the normal chat endpoint, `POST /api/message`; whether that is an approval is decided by the approval guard
  reading the message, exactly as if you had typed it. No other route can approve, execute or propose anything.
- **My bookings** is what `list_bookings` returned, through the same contract tools the agent uses.
- **Proactive cancellations appear with no user message:** the server polls on a timer (`--poll-seconds`, default 3)
  and the page picks up notices and trace rows by polling `/api/log` about once a second. A poll is skipped while a
  message is running, and a message that arrives during a poll waits, so the two never interleave. The chat endpoint
  is a plain `def`, so a slow model call runs in a worker thread and does not block the server or the timer.
- The buttons call the same simulator hooks as the CLI commands (they are not agent tools). "Provider cancels" only
  cancels the booking; the agent notices on its next poll.
- Do not run the CLI and the web server on the same `--data-dir` at the same time (two processes, one SQLite file).

## Configuration

Create `.env` (never committed; `.env.example` is the template). The key is read from the environment by python-dotenv
and the SDK, and is never printed or traced.

| Variable | Meaning | Default |
|---|---|---|
| `ANTHROPIC_API_KEY` | API key | required for the demo |
| `MODEL_NAME` | model id | `claude-sonnet-5-5` |
| `MODEL_EFFORT` | `low` / `medium` / `high` / `none` (do not send) | `medium` |
| `MODEL_THINKING` | `between_tools` / `none` (do not send) | `between_tools` |
| `MODEL_MAX_TOKENS`, `MODEL_TIMEOUT_S` | per request | `2048`, `20` |
| `PRICE_INPUT_PER_MTOK`, `PRICE_OUTPUT_PER_MTOK` | override the active model's prices (USD per 1M tokens) | `errand/config.py` |

Costs in traces are **estimates**: the price table in `errand/config.py` (claude-sonnet-5-5: $2 per million input
tokens, $10 per million output tokens) times the token counts the API reports. Cache tokens are recorded but not
priced. If the API rejects the thinking or effort setting, the client steps down to the simplest setting it accepts
and records a `model_setting_fallback` event; it never echoes thinking blocks.

## Layout

- `errand/core/` approval guard, idempotent executor, startup recovery; `errand/agent/` graph, tools, `finalize`,
  context builder, proactive poller; `errand/memory/`; `errand/model/` (`ScriptedModel`, `AnthropicClient`);
  `errand/trace/`; `errand/app.py` (composition); `errand/config.py`.
- `errand/mocks/` the marketplace and its simulator hooks. The agent reaches it only through `errand/wiring.py`,
  and `tests/test_boundaries.py` enforces that.
- `demo/` the terminal demo (`chat.py`) and the web UI (`web/`); it lives outside `errand/` because it uses the
  simulator hooks.
- `tests/` offline tests; `tests/evals/` the scenarios that write the eval table.

## Known limitations

- SQLite only: the optional Postgres / docker-compose setup is not implemented.
- `AnthropicClient` is covered offline against a fake SDK client. The live API path (including the thinking setting) is
  exercised only by running the demo with a key.
- Proactive polling runs between CLI inputs, or on a timer in the web server (skipped while a message is running);
  there is no separate worker process. A replacement proposal expires after 15 minutes and its hold after 10.
- Memory ranking is tags plus keyword overlap (no embeddings). Only the seed creates inferred memories; the agent does
  not guess new ones, though seeded ones can be confirmed or rejected.
- A message's own tool results are never trimmed, so one that gathers more than the 3,000-token context budget ends as
  `LIMIT_REACHED` (scenario C3).
- One seeded demo user.
